1. Overview & Goal

TrackMP currently uses a React frontend built with Create React App (CRA) and React Router. We are migrating to Next.js 14 (App Router) to improve search engine visibility (SEO) and performance.

✅ The backend (FastAPI + MongoDB) stays unchanged. Only the frontend is rebuilt.

🎯 Goal: A fully working Next.js app that looks and behaves exactly like the old one, but with server‑rendered politician and article pages for better Google rankings and social previews.

2. Glossary (Plain‑English Terms)

TermWhat it means in simple words
FrontendThe part people see and click (pages, buttons, forms).
Backend / APIStores and processes data (FastAPI + MongoDB). Stays the same.
Next.jsThe new framework/tool we're switching the frontend to.
CRACreate React App — the old tool the current frontend was built with.
Server ComponentA page built on the server (fast, great for SEO).
Client ComponentRuns in the visitor's browser (needed for buttons, forms, interactive stuff).

RollbackUndoing the switch and going back to the old working version.

3. Overall Strategy

🧪 Test server first! Instead of changing the live site directly, we take a full backup, set up a separate test server, do the entire migration there, and only bring the finished result back to production.

Since the live website’s data will not change during the migration (no new signups, submissions, or admin edits while we work), one backup at the start is enough — no need to keep data in sync.

4. Step 1 — Backup Everything

On the production server (as root), back up three things:

  1. App code — FastAPI backend + React frontend folders
  2. Database — full MongoDB dump (politicians, articles, promises, users, comments, etc.)
  3. Uploaded files — politician photos, article images, ticket attachments, promise attachments
mkdir -p /opt/trackmp-backup-$(date +%Y%m%d)
cd /opt/trackmp-backup-$(date +%Y%m%d)

# 1. App code (exclude node_modules, caches)
rsync -a --exclude='node_modules' --exclude='__pycache__' --exclude='venv' \
  --exclude='build' /opt/trackmp/ ./trackmp-code/

# 2. Database dump
mongodump --uri="mongodb://localhost:27017/trackmp_db" --out=./mongo-dump/

# 3. Uploaded media files
rsync -a /opt/trackmp/backend/uploads/ ./uploads/
rsync -a /opt/trackmp/politician_media/ ./politician_media/ 2>/dev/null
rsync -a /opt/trackmp/article_media/ ./article_media/ 2>/dev/null
rsync -a /opt/trackmp/ticket_attachments/ ./ticket_attachments/ 2>/dev/null
rsync -a /opt/trackmp/promise_media/ ./promise_media/ 2>/dev/null

# 4. Compress everything into one file
tar czf /root/trackmp-full-backup-$(date +%Y%m%d).tar.gz .
📋 Also save separately (outside code folder):
  • .env file (secrets/passwords) — but do not reuse these secrets on the test server (see security note below).
  • systemd service files (backend/frontend)
  • nginx configuration file
  • Sitemap XML files (sitemap.xml, sitemap-politicians-*.xml)
🔐 Security: Because the test server will be reachable over the internet, generate brand‑new secret keys there (JWT_SECRET, VOICE_HMAC_SECRET, RECAPTCHA_SECRET_KEY). Do not copy production secrets. This is also a good chance to rotate the flagged production secrets later.

5. Step 2 — Set Up the Test Server

On the test server, install the same versions of Python, Node.js, MongoDB, and nginx as production to avoid “works on one server but not the other” issues.

# Copy the backup file to the test server, then:
tar xzf trackmp-full-backup-*.tar.gz -C /opt/trackmp/

# Restore the database
mongorestore --uri="mongodb://localhost:27017/trackmp_db" ./mongo-dump/trackmp_db/

# Restore uploaded files
rsync -a ./uploads/ /opt/trackmp/backend/uploads/
# (repeat for other media folders: politician_media, article_media, etc.)
✅ Sanity check: Before touching anything, get the existing, unmodified CRA website running correctly on the test server. If that works, you know the backup/restore is solid — any later problems are from the migration, not a bad backup.

6. Step 3 — Install Next.js (Phase 1)

Create a brand‑new Next.js project alongside the existing frontend folder — this avoids conflicts between the old build tool (Craco) and the new one.

cd /opt/trackmp
npx create-next-app@latest frontend-next --js --tailwind --eslint --app --src-dir --import-alias "@/*"

Copy over, unchanged: Shadcn UI components, Tailwind design colors/fonts, and any plain helpers that don’t depend on React Router (e.g. api.js, format.js).

Remove: craco, react-router-dom, react-scripts.
Add: next (version 14).

Set up a rewrite so the new frontend can talk to the FastAPI backend immediately:

// frontend-next/next.config.js
module.exports = {
  async rewrites() {
    return [{
      source: '/api/:path*',
      destination: `${process.env.BACKEND_URL || 'http://127.0.0.1:8001'}/api/:path*`,
    }];
  },
};

7. Step 4 — Reorganize Pages (Phase 2)

Each existing page moves into a new folder structure. Every page gets its own folder with a page.jsx file.

Old fileNew location
HomePage.jsxapp/page.jsx
AboutPage.jsxapp/about/page.jsx
PoliticianProfile.jsxapp/politicians/[slug]/page.jsx
ArticleDetail.jsxapp/articles/[id]/page.jsx
ContactPage.jsxapp/contact/page.jsx
LoginPage.jsxapp/(auth)/login/page.jsx
dashboard/* (all admin pages)app/(dashboard)/dashboard/*

The admin dashboard pages share a single “logged‑in” layout and permission check via the (dashboard) group folder.

The old PublicLayout.jsx and DashboardLayout.jsx become layout.jsx files that wrap groups automatically.

8. Step 5 — Client vs Server Components (Phase 3)

This is the biggest conceptual change. Next.js pages are server‑rendered by default (faster, better for SEO) — but interactive parts (buttons, forms, dropdowns) still need to run in the browser.

Must be “Client Components” (add 'use client' at the top):

  • UI library components (buttons, dialogs, dropdowns)
  • Login/theme context providers
  • Any form with typing, file uploads, or reCAPTCHA
  • The entire admin dashboard (mostly interactive tables/forms)

Convert to “Server Components” (fetch data on the server):

  • Politician profile page — fetch data on the server, then pass to a smaller interactive component for tabs
  • Article detail page — same pattern
💡 The Promises‑tab work pairs naturally: the extracted tab component can be lazy‑loaded with next/dynamic (Next.js’s version of React.lazy).

9. Step 6 — SEO & Metadata (Phase 4)

This is the main reason for the migration — making politician and article pages rank better in Google and show rich previews on social media.

  • Each politician/article page uses generateMetadata() to produce title, description, and social‑share image automatically from that politician’s data.
  • Structured data (invisible code that tells Google “this is a person, here’s their job”) is added directly into the page.
🗺️ Sitemaps stay as‑is. The existing Python sitemap‑generation script handles the large number of politician records well (chunked into multiple files). We keep that system — Next.js only generates sitemap entries for static pages (Home, About, Contact).

10. Step 7 — Connect to FastAPI Backend (Phase 5)

Traffic routing: nginx keeps sending /api/... requests to FastAPI (port 8001). Everything else goes to the Next.js app (port 3000).

location /api/ {
    proxy_pass http://127.0.0.1:8001;
}
location / {
    proxy_pass http://127.0.0.1:3000;
}

Authentication change: Currently the login token is stored in browser localStorage. Server‑rendered pages can’t read localStorage. The fix: switch to storing the token in a secure, http‑only cookie set by FastAPI on login. Both server and browser can then read it.

Bonus: with this change, we can add middleware that blocks access to /dashboard/... pages before they load if the user isn’t logged in — preventing the “flash” of a page that then redirects.

11. Step 8 — Testing Checklist (on test server)

  • ☐ Homepage loads with correct design (colors, animations, stats)
  • ☐ Politician profile page loads, and “View Page Source” shows the politician’s name/info in the raw HTML (proves SSR works)
  • ☐ Social share preview looks right when pasting a politician page link into WhatsApp/Twitter/Facebook
  • ☐ Search and filters on politicians list still work
  • ☐ Login works, and staying logged in across a page refresh works
  • ☐ Admin dashboard: politicians list, edit, admin management, audit log, voice moderation all load correctly
  • ☐ Submitting a contact form / update / voice comment (with reCAPTCHA) works
  • ☐ Trying to open a dashboard page while logged out correctly redirects to login
  • ☐ Old URLs (bookmarked links, Google links) still lead to the correct page and don’t show broken links
  • ☐ Mobile view looks correct on a phone or narrow browser window
  • ☐ sitemap.xml still loads and lists politician pages correctly

12. Step 9 — Going Live (Cutover)

Once everything passes on the test server, moving to production is mostly copying files and flipping a switch in nginx — the live database was never touched, so there’s no data to move back.

# On the production server

# 1. Stop the old frontend service
systemctl stop trackmp-frontend

# 2. Copy the finished Next.js app from the test server
rsync -a testserver:/opt/trackmp/frontend-next/ /opt/trackmp/frontend-next/
cd /opt/trackmp/frontend-next
npm run build

# 3. Set up and start the new service
systemctl daemon-reload
systemctl start trackmp-nextjs
systemctl enable trackmp-nextjs

# 4. Switch nginx to point to the new app, then reload
nginx -t && systemctl reload nginx

# 5. Ensure backend is still running
systemctl start trackmp-backend
⏰ Pick a low‑traffic time window (e.g. late night) for the switch, in case there’s a brief interruption.

13. Step 10 — Rollback Plan (if something breaks)

Do not delete the old frontend folder — keep it for at least a week as an instant safety net.

If something goes wrong, reverting takes one minute:

# Point nginx back at the old app
# (edit nginx config: proxy_pass back to the old CRA build port)
nginx -t && systemctl reload nginx

# Restart the old frontend service
systemctl start trackmp-frontend

Since the database was never modified during migration, there is no data to “undo” — rollback is purely a code/service switch.

14. Step 11 — After Launch

  • ☐ Watch server logs for the first few hours (journalctl -u trackmp-nextjs -f)
  • ☐ Check Google Search Console over the following weeks for crawl errors
  • ☐ Confirm social sharing previews work correctly on the live domain (not just test server)
  • ☐ Once confident everything is stable (a week or two), archive and remove the old CRA frontend folder
  • ☐ Rotate the flagged production secrets (JWT_SECRET, VOICE_HMAC_SECRET, RECAPTCHA_SECRET_KEY) if not already done

15. Extra Points Worth Considering

  • SSL/HTTPS certificates — ensure the test server has its own certificate (or is accessed by IP/hosts‑file) so you’re not accidentally reusing the production domain’s certificate.
  • Environment variables checklist — before cutover, list every value in the old .env and confirm each one has an equivalent set on the new Next.js app (backend URL, recaptcha site key, etc.) so nothing is silently missing.
  • DNS/caching — if using a CDN or Cloudflare, remember cached pages may need purging right after cutover so visitors see the new version immediately.
  • Team/staff notice — give admins a heads‑up about the cutover window so they’re not mid‑edit when the switch happens.
  • Browser cache for returning visitors — not usually an issue for server‑rendered pages, but spot‑check that returning visitors aren’t shown a broken mixed old/new version.
  • Keep the migration out of Git history mess — consider doing the Next.js work in its own git branch/repo so the eventual merge into your main project is a clean, reviewable diff.
