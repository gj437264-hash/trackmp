SEO Task Automation Setup Guide

From standalone scripts to a scheduled, monitored, fault-tolerant service — full build steps and troubleshooting reference.

What this covers: consolidating several standalone Python maintenance scripts (slug backfill, static page generation, sitemap generation) into a single installable package with shared configuration, logging, retries, locking, and a systemd timer — plus every real error encountered while deploying this pattern and how it was diagnosed.

Architecture

One Python package with subcommands, run via python -m <package>.cli run-all, scheduled with a systemd timer (preferred over cron on any systemd-managed Linux host — it gives locking semantics, structured logs via journalctl, and failure hooks for free).

OptionVerdict
Separate standalone scriptsRejectedEach script re-implements DB connection, config loading, and logging — the exact drift that causes crashes when one script uses a different env var name than another.
Bash wrapper around Python scriptsRejectedLocking, retries, and structured error handling are all easier and safer in Python; Bash should glue processes, not own logic.
Pure Bash implementationRejectedNo safe way to do DB queries or templated file generation without shelling out to Python anyway.
Single Python package, subcommands, systemd timerRecommendedShared config/logging/db modules eliminate drift; systemd timer provides locking, logs, and failure hooks natively.

Directory Structure

Replace /app/seo-tasks below with your actual install path.

/app/seo-tasks/ ├── seo_tasks/ <- the importable package (underscore required) │ ├── __init__.py │ ├── cli.py <- entrypoint: run-all | backfill-slugs | static-pages | sitemap │ ├── config.py <- loads & validates ALL env vars in one place │ ├── db.py <- single get_db() with connection handling │ ├── logging_setup.py <- rotating file + console logging │ ├── notify.py <- Slack webhook notifications │ ├── lockfile.py <- flock-based single-instance guard │ ├── retry.py <- @retry decorator for transient failures │ ├── atomic_write.py <- tmp-file + os.replace() safe writer │ ├── state.py <- tracks last-run timestamps in MongoDB │ └── tasks/ │ ├── __init__.py │ ├── backfill_slugs.py │ ├── static_pages.py │ └── sitemap.py ├── venv/ <- Python virtual environment ├── logs/ <- rotated log files (must exist before first run) ├── run/ <- lock file directory (must exist before first run) ├── .env <- chmod 600, one canonical var per setting └── systemd/ ├── app-seo.service └── app-seo.timer
The single most common failure in this setup traces back to two things: (1) the package folder must be named with an underscore (seo_tasks), never a hyphen — Python module names cannot contain hyphens — and (2) whatever path you choose for the parent folder, it must be used consistently across the systemd unit's WorkingDirectory, EnvironmentFile, and ExecStart lines. A hyphen/underscore mismatch between the parent folder and the package folder, or between what the unit file expects and what actually exists on disk, causes almost every early error in this guide.

Step 1 — Create the user and directories

# Dedicated low-privilege service account (least-privilege, not root)
useradd --system --home /app/seo-tasks --shell /usr/sbin/nologin svcuser

mkdir -p /app/seo-tasks/logs /app/seo-tasks/run
mkdir -p /app/seo-tasks/seo_tasks/tasks

chown -R svcuser:svcuser /app/seo-tasks
Use mkdir -p dir1 dir2 as two separate arguments, not brace syntax like mkdir -p {logs,run}, if there is any chance this will be run with sh instead of bash. Brace expansion is a bash-only feature — under dash/sh it is treated as a literal string and creates a single directory literally named {logs,run} instead of two real directories. See Troubleshooting: brace expansion.

Step 2 — Virtual environment

cd /app/seo-tasks
python3 -m venv venv
./venv/bin/pip install pymongo

No other third-party dependencies are required — logging, retries, locking, and notifications can all be built on the Python standard library (logging, fcntl, tempfile, urllib).

Step 3 — Shared modules

These live in seo_tasks/ directly (not in tasks/) and are imported by every task module. Writing config/DB/logging once here — instead of duplicating it in each task — is what prevents the env-var drift that causes most production incidents in this kind of setup.

config.py — single source of truth for all settings

import os
import sys
from dataclasses import dataclass

@dataclass(frozen=True)
class Settings:
    mongodb_uri: str
    mongodb_db: str
    base_url: str
    sitemap_output_dir: str
    static_output_dir: str
    slack_webhook_url: str | None

def load_settings() -> Settings:
    required = ["MONGODB_URI", "MONGODB_DB", "BASE_URL"]
    missing = [k for k in required if not os.environ.get(k)]
    if missing:
        sys.stderr.write(f"FATAL: missing required env vars: {', '.join(missing)}\n")
        sys.exit(1)

    return Settings(
        mongodb_uri=os.environ["MONGODB_URI"],
        mongodb_db=os.environ["MONGODB_DB"],
        base_url=os.environ["BASE_URL"],
        sitemap_output_dir=os.environ.get("SITEMAP_OUTPUT_DIR", "/app/public"),
        static_output_dir=os.environ.get("STATIC_OUTPUT_DIR", "/app/public/politicians"),
        slack_webhook_url=os.environ.get("SLACK_WEBHOOK_URL"),
    )

db.py — one connection helper

from functools import lru_cache
from pymongo import MongoClient
from pymongo.errors import PyMongoError
from .config import load_settings
from .retry import retry

@lru_cache
def get_client() -> MongoClient:
    settings = load_settings()
    return MongoClient(settings.mongodb_uri, serverSelectionTimeoutMS=5000)

def get_db():
    settings = load_settings()
    return get_client()[settings.mongodb_db]

@retry(exceptions=(PyMongoError,), attempts=3, base_delay=2)
def ping():
    get_client().admin.command("ping")

retry.py

import time
import logging
import functools

def retry(exceptions, attempts=3, base_delay=2):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            log = logging.getLogger(fn.__module__)
            for attempt in range(1, attempts + 1):
                try:
                    return fn(*args, **kwargs)
                except exceptions as e:
                    if attempt == attempts:
                        log.error(f"{fn.__name__} failed after {attempts} attempts: {e}")
                        raise
                    delay = base_delay * (2 ** (attempt - 1))
                    log.warning(f"{fn.__name__} failed (attempt {attempt}/{attempts}): {e} — retrying in {delay}s")
                    time.sleep(delay)
        return wrapper
    return decorator

atomic_write.py — never publish a truncated file

import os
import tempfile

def atomic_write(path: str, content: str, encoding="utf-8"):
    directory = os.path.dirname(path)
    fd, tmp_path = tempfile.mkstemp(dir=directory, prefix=".tmp-")
    try:
        with os.fdopen(fd, "w", encoding=encoding) as f:
            f.write(content)
        os.replace(tmp_path, path)  # atomic on the same filesystem
    except Exception:
        if os.path.exists(tmp_path):
            os.remove(tmp_path)
        raise

lockfile.py — prevent overlapping runs

import fcntl
import os
import sys

class SingleInstance:
    def __init__(self, path="run/seo-tasks.lock"):
        self.path = path
        self.fh = None

    def __enter__(self):
        os.makedirs(os.path.dirname(self.path), exist_ok=True)
        self.fh = open(self.path, "w")
        try:
            fcntl.flock(self.fh, fcntl.LOCK_EX | fcntl.LOCK_NB)
        except BlockingIOError:
            sys.stderr.write("Another run is already in progress — exiting.\n")
            sys.exit(3)  # distinct code: "skipped", not "failed"
        self.fh.write(str(os.getpid()))
        self.fh.flush()
        return self

    def __exit__(self, *a):
        fcntl.flock(self.fh, fcntl.LOCK_UN)
        self.fh.close()

Uses flock, which releases automatically if the holding process dies — a stale PID left in the lock file after a crash is harmless and self-heals on the next run.

state.py — enables change detection instead of full reprocessing every run

from datetime import datetime, timezone
from .db import get_db

def get_last_run(task_name: str):
    doc = get_db()["seo_state"].find_one({"_id": task_name})
    return doc["last_run"] if doc else None

def set_last_run(task_name: str, when: datetime = None):
    when = when or datetime.now(timezone.utc)
    get_db()["seo_state"].update_one(
        {"_id": task_name}, {"$set": {"last_run": when}}, upsert=True
    )

logging_setup.py — path-independent, self-healing

import logging
from pathlib import Path
from logging.handlers import RotatingFileHandler

def setup_logging():
    root = logging.getLogger()
    root.setLevel(logging.INFO)

    fmt = logging.Formatter("%(asctime)s %(levelname)s %(name)s: %(message)s")

    # Resolved relative to this file's location, NOT the process's working
    # directory — avoids failures if the process is ever launched from
    # somewhere unexpected.
    log_dir = Path(__file__).resolve().parent.parent / "logs"
    log_dir.mkdir(parents=True, exist_ok=True)

    file_handler = RotatingFileHandler(
        log_dir / "seo-tasks.log", maxBytes=10 * 1024 * 1024, backupCount=5
    )
    file_handler.setFormatter(fmt)
    root.addHandler(file_handler)

    console = logging.StreamHandler()  # captured by journald under systemd
    console.setFormatter(fmt)
    root.addHandler(console)

notify.py — Slack alerts, stdlib only

import json
import logging
import urllib.request
from .config import load_settings

def slack_notify(message: str):
    settings = load_settings()
    if not settings.slack_webhook_url:
        return
    try:
        req = urllib.request.Request(
            settings.slack_webhook_url,
            data=json.dumps({"text": message}).encode(),
            headers={"Content-Type": "application/json"},
        )
        urllib.request.urlopen(req, timeout=5)
    except Exception as e:
        logging.getLogger(__name__).warning(f"Slack notify failed: {e}")

Step 4 — Task modules

Each file in seo_tasks/tasks/ exposes a single run() -> bool function and imports shared modules with relative imports (from ..db import get_db). No task module should ever read os.environ directly — always go through config.load_settings().

When merging old standalone scripts into this structure, delete the original script's body entirely rather than appending the new function above it. See Troubleshooting: leftover dead code after merge — this was the single most disruptive class of bug encountered during migration. 
# seo_tasks/tasks/backfill_slugs.py — example shape
import logging
from ..db import get_db
from ..retry import retry
from pymongo.errors import PyMongoError

log = logging.getLogger(__name__)

@retry(exceptions=(PyMongoError,), attempts=3, base_delay=2)
def run() -> bool:
    db = get_db()
    # ... task logic here, using db directly ...
    log.info("Task complete")
    return True

Step 5 — CLI entrypoint

# seo_tasks/cli.py
import argparse
import sys
import logging
from .logging_setup import setup_logging
from .lockfile import SingleInstance
from .notify import slack_notify
from .tasks import backfill_slugs, static_pages, sitemap

TASKS = {
    "backfill-slugs": backfill_slugs.run,
    "static-pages": static_pages.run,
    "sitemap": sitemap.run,
}

def run_all():
    results = {}
    for name, fn in TASKS.items():
        try:
            results[name] = fn()
        except Exception as e:
            logging.getLogger(name).exception(f"{name} failed")
            slack_notify(f":x: SEO task `{name}` failed: {e}")
            results[name] = False
    if all(results.values()):
        return 0
    if any(results.values()):
        return 2   # partial failure
    return 1        # total failure

def main():
    parser = argparse.ArgumentParser(prog="seo-tasks")
    sub = parser.add_subparsers(dest="command", required=True)
    sub.add_parser("run-all")
    for name in TASKS:
        sub.add_parser(name)
    args = parser.parse_args()

    setup_logging()
    with SingleInstance(path="run/seo-tasks.lock"):
        if args.command == "run-all":
            sys.exit(run_all())
        else:
            sys.exit(0 if TASKS[args.command]() else 1)

if __name__ == "__main__":
    main()

Step 6 — .env configuration

cat > /app/seo-tasks/.env <<'EOF'
MONGODB_URI=mongodb://localhost:27017
MONGODB_DB=appdb
BASE_URL=https://your-real-domain.com
SITEMAP_OUTPUT_DIR=/app/public
STATIC_OUTPUT_DIR=/app/public/politicians
SLACK_WEBHOOK_URL=
EOF
chmod 600 /app/seo-tasks/.env
chown svcuser:svcuser /app/seo-tasks/.env
Use exactly one variable name per setting, everywhere. If one script reads MONGODB_DB and another reads MONGODB_DATABASE, you will get intermittent KeyError crashes that look unrelated to each other. Grep the whole codebase for every place an env var is read and standardize on a single name before deploying: grep -rn 'os.environ\[' seo_tasks/

Step 7 — systemd units

app-seo.service

[Unit]
Description=App SEO maintenance (slugs, static pages, sitemap)
After=network-online.target mongod.service
Wants=network-online.target
OnFailure=app-seo-alert.service

[Service]
Type=oneshot
User=svcuser
Group=svcuser
WorkingDirectory=/app/seo-tasks
EnvironmentFile=/app/seo-tasks/.env
ExecStart=/app/seo-tasks/venv/bin/python -m seo_tasks.cli run-all
TimeoutStartSec=30min
OnFailure= is a [Unit] directive, not a [Service] directive. Putting it under [Service] does not cause a hard failure — systemd silently ignores the unknown key and logs a warning — so this mistake is easy to miss. See Troubleshooting: OnFailure= ignored.

app-seo.timer

[Unit]
Description=Run App SEO maintenance daily

[Timer]
OnCalendar=*-*-* 03:00:00
RandomizedDelaySec=300
Persistent=true

[Install]
WantedBy=timers.target

Persistent=true means a run missed due to the host being down at the scheduled time fires automatically at next boot, instead of silently skipping that day.

app-seo-alert.service (optional but referenced above)

[Unit]
Description=Alert on app-seo failure

[Service]
Type=oneshot
EnvironmentFile=/app/seo-tasks/.env
ExecStart=/app/seo-tasks/venv/bin/python -m seo_tasks.notify_failure
If OnFailure= references a unit that references a Python entrypoint that doesn't exist yet, the failure path is a silent no-op rather than a hard error. Either implement notify_failure as a small CLI subcommand, or remove the OnFailure= line until you do — don't leave it half-wired.

Step 8 — Enable and do a first verification

cp systemd/app-seo.service systemd/app-seo.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now app-seo.timer

systemctl list-timers app-seo.timer
systemctl start app-seo.service     # manual first run
journalctl -u app-seo.service -f

Manual testing (before trusting systemd)

Running the CLI directly with sudo -u svcuser does not load .env — EnvironmentFile= is a systemd-only mechanism. To get a fair manual test that mirrors what systemd will actually do:

cd /app/seo-tasks
sudo -u svcuser env $(grep -v '^#' .env | xargs) ./venv/bin/python -m seo_tasks.cli run-all
This simple form breaks if any value in .env contains spaces or quotes. If that becomes a problem, switch to: 
sudo -u svcuser bash -c 'set -a; source .env; set +a; ./venv/bin/python -m seo_tasks.cli run-all'

Troubleshooting Reference

Each entry below is a real failure mode encountered while building and deploying this exact pattern, in the order they tend to surface.

Setupmkdir created a directory literally named {logs,run}

ls __init__.py atomic_write.py cli.py config.py ... {logs,run}

Cause: a deployment script used mkdir -p /app/seo-tasks/{logs,run} but was executed with sh script.sh. Brace expansion is a bash feature; dash (what sh usually points to on Debian/Ubuntu) treats {logs,run} as a literal string. Only one directory gets created, with that exact literal name — logs/ and run/ never exist, which later causes logging and lock-file errors.

Fix:

mkdir -p /app/seo-tasks/logs /app/seo-tasks/run
rm -rf "/app/seo-tasks/{logs,run}"   # remove the bogus literal directory

Prevention: always run deployment scripts with bash script.sh, or avoid brace expansion in any script that might be run with plain sh.

SetupPath name inconsistency (hyphen vs underscore, or different parent dirs)

Failed to load environment files: No such file or directory Failed to spawn 'start' task: No such file or directory status=203/EXEC

Cause: the actual directory on disk (e.g. /app/seo-tasks) doesn't match what the systemd unit file's WorkingDirectory=, EnvironmentFile=, or ExecStart= expect (e.g. /app/seo_tasks). This is extremely easy to introduce because the *parent* folder name is arbitrary (hyphen or underscore, either is fine) but the *package* folder underneath it (imported via -m seo_tasks.cli) must always be underscored — mixing these two naming decisions up is the most common source of this bug.

Fix: pick one parent path and use it verbatim in every reference:

grep -rn "/app/seo" /etc/systemd/system/app-seo.service
ls /app/seo-tasks/seo_tasks/cli.py   # must exist exactly at this path
ls /app/seo-tasks/.env
ls /app/seo-tasks/venv/bin/python

All three ls checks above must succeed before starting the service. If any fail, either move the files or edit the unit file — don't guess.

ImportModuleNotFoundError: No module named 'seo_tasks'

python: Error while finding module specification for 'seo_tasks.cli' (ModuleNotFoundError: No module named 'seo_tasks')

Cause: either (a) the command was run from a directory that doesn't contain a folder literally named seo_tasks — e.g. running from /tmp instead of the app root — or (b) the package files are sitting flat in the app root instead of nested inside a seo_tasks/ subfolder. python -m pkg.module requires pkg/ to be importable from the current working directory (or on PYTHONPATH).

Fix:

cd /app/seo-tasks   # must be the parent of seo_tasks/, not seo_tasks/ itself
mkdir -p seo_tasks
mv __init__.py cli.py config.py db.py atomic_write.py lockfile.py \
   logging_setup.py notify.py retry.py state.py tasks seo_tasks/
ls seo_tasks/         # confirm cli.py etc. are now nested one level down

systemdFailed to load environment files: No such file or directory

Cause: EnvironmentFile= in the unit points at a path that doesn't exist — usually the same root cause as the path mismatch above, specific to the .env file.

Fix: confirm the exact path, then reload:

ls -l /app/seo-tasks/.env
# edit EnvironmentFile= in the unit to match exactly
systemctl daemon-reload
systemctl restart app-seo.service

ConfigFATAL: missing required env vars when running manually

FATAL: missing required env vars: MONGODB_URI, MONGODB_DB, BASE_URL

Cause: this is expected, not a bug, when running the CLI directly (e.g. sudo -u svcuser ./venv/bin/python -m seo_tasks.cli run-all) without loading .env first. EnvironmentFile= is systemd-only — nothing automatically sources .env for a manually-invoked process.

Fix: inject the same variables manually for a fair test:

sudo -u svcuser env $(grep -v '^#' .env | xargs) ./venv/bin/python -m seo_tasks.cli run-all

If this succeeds but the systemd-triggered run still fails, the problem is specific to the unit file (see EnvironmentFile not found), not the application code.

systemdUnknown key name 'OnFailure' in section 'Service', ignoring

Cause: OnFailure= belongs in [Unit], not [Service]. systemd doesn't hard-fail on an unrecognized key in the wrong section — it logs a warning and silently ignores the directive, so failure alerting quietly does nothing until someone notices it in the logs.

Fix: move it to the [Unit] block:

[Unit]
Description=...
OnFailure=app-seo-alert.service

[Service]
...

CodeTypeError: function() takes N positional arguments but M were given

TypeError: unique_slug_for() takes 3 positional arguments but 4 were given

Cause: two definitions of the same function name exist in one module (usually from pasting a new implementation above an old one without deleting the old one). Python does not error on redefinition — the second definition silently overwrites the first in the module namespace, so a call written against the new signature can end up executing the old function body.

Fix: search for duplicate definitions and delete the stale one entirely:

grep -n "^def " seo_tasks/tasks/*.py

If a function name appears twice in the same file's output, the file needs to be rewritten to keep only the current version.

CodeTask silently doing the wrong thing (or nothing) after a merge

INFO sitemap: Documents missing a slug: 0 INFO sitemap: Nothing to do.

Cause: when merging an old standalone script into the new task-module structure, only the top of the file was replaced — the rest of the original script's body (a second main(), unused imports, references to variables like BASE_URL/OUTPUT_DIR that were commented out) was left in place below it. Because the new run() function returns before ever reaching that code, it never executes — but because it was copy-pasted from a different task file, the logging messages are misleading (a sitemap task logging about "missing a slug" is the tell).

Fix: for any task file that shows log output referencing the wrong task's concern, open the file and check for leftover code after the real run() function:

grep -n "def run\|def main\|MongoClient" seo_tasks/tasks/*.py

Any file showing more than one def run/def main, or a MongoClient(...) call outside db.py, needs to be rewritten from scratch rather than patched — partial merges are hard to trust once found once.

RuntimeVerifying the lock file actually prevents concurrent runs

Not a bug report — a test worth running deliberately, since it's easy to configure a lock file that's never actually exercised until two runs genuinely overlap in production.

Test:

# Terminal 1 — start a run and let it hold the lock
sudo -u svcuser env $(grep -v '^#' .env | xargs) ./venv/bin/python -m seo_tasks.cli run-all &

# Terminal 2 — immediately try a second run
sudo -u svcuser env $(grep -v '^#' .env | xargs) ./venv/bin/python -m seo_tasks.cli run-all
echo $?   # should print 3 (skipped, lock held) — not hang, not error

RuntimePermission errors writing to public output directories

Cause: the service account (e.g. svcuser) lacks write access to SITEMAP_OUTPUT_DIR / STATIC_OUTPUT_DIR, commonly because those directories were created earlier while logged in as root.

Test before a full run:

sudo -u svcuser touch /app/public/permtest && rm /app/public/permtest
echo $?   # 0 means write access is fine

Note: os.replace() (used by atomic_write.py) only needs write permission on the containing directory, not ownership of the specific file being replaced — so this test is usually sufficient even if existing files in that directory are still root-owned.

Pre-flight checklist before enabling the timer

  • Package folder is named with an underscore and sits one level under the working directory (/app/seo-tasks/seo_tasks/cli.py exists)
  • logs/ and run/ exist as real directories, not a literal {logs,run} folder
  • Every env var is read through config.py — no task module calls os.environ[...] directly (grep -rn "os.environ\[" seo_tasks/ returns nothing outside config.py)
  • Manual run with injected .env succeeds and produces real, non-placeholder output
  • BASE_URL in .env is the real domain, not a placeholder
  • Every task file has exactly one def run() and no leftover def main() from the original script
  • OnFailure= is under [Unit], and the unit it references actually exists
  • Manual systemctl start shows status=0/SUCCESS and matches the manual test's behavior
  • Lock file correctly rejects a second concurrent run with exit code 3
  • Service account has confirmed write access to every output directory
Internal reference document — update paths, service account name, and unit filenames to match your actual deployment before distributing further.
